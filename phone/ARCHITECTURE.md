# Архитектура Remo32

Документ объясняет, из чего состоит система, почему выбраны именно эти
решения и где проходят границы ответственности. Всё, что здесь написано,
относится к состоянию на 29 августа 2026 года.

---

## 1. Задача и ограничения

Управлять двумя домашними ПК с телефона: видеть состояние, включать,
выключать, запускать программы, при необходимости попадать в терминал.

Ограничения, которые определили архитектуру больше, чем любые
предпочтения:

| Ограничение | Следствие |
|---|---|
| Основной ПК **работает постоянно** (перезагрузка примерно раз в неделю) | Контроллер живёт на нём; он же будит второй ПК |
| Этот же ПК — единственная точка отказа всей системы | Плата ESP32 следит за ним и поднимает сама, без телефона |
| Роутер — ZTE ZXHN H3600P от провайдера DIGI, OpenWrt на него не ставится | Роутер не может стать узлом системы |
| ESP32 не умеет Tailscale | Телефон снаружи не дотянется до платы напрямую |
| Публичный IPv4 есть, UPnP выключен, глобального IPv6 нет | Проброс порта возможен, но только руками |
| Платы физически не было в начале разработки | Симулятор обязателен, а не желателен |
| PSRAM на плате **неисправен** (проверено 2026-09-03, см. ниже) | Прошивка собирается с `CONFIG_SPIRAM` выключенным |

## 2. Общая схема

```
              ТЕЛЕФОН
                 │  HTTPS + сессия (passkey или пароль)
                 │
            [ Tailscale ]        ← шифрованная частная сеть
                 │
                 ▼
    ОСНОВНОЙ ПК (включён всегда)
    ┌──────────────────────────────┐
    │  ЦЕНТРАЛЬНЫЙ КОНТРОЛЛЕР      │
    │  FastAPI + мобильный UI      │
    │  + планировщик расписаний    │
    │  АГЕНТ этого же ПК           │
    └───┬──────────────────────┬───┘
        │ токен агента         │ транспорт ESP32
        │                      │ (mock | http | mqtt)
        ▼                      ▼
   АГЕНТ ПК #2            ESP32 / СИМУЛЯТОР
   (шумный сервер)        ├── Wake-on-LAN в LAN
   ├ статистика           ├── СТОРОЖ основного ПК
   ├ действия             ├── чтение LED питания
   ├ питание              └── (позже) KVM, реле, датчики
   └ терминал (tmux)              │
        ▲                         │
        └── magic packet ─────────┘
            (обычно шлёт контроллер,
             плата — только страховка)
```

**Провал в этой схеме и чем он закрыт.** Контроллер работает на том самом
ПК, который может умереть: пропало электричество, зависание после недели
аптайма, неудачная перезагрузка. Разбудить его с телефона невозможно —
командовать некому. Единственное устройство, способное помочь, должно
действовать **само**. Поэтому плата не пульт, а сторож: она пингует
основной ПК и, если тот молчит дольше заданного времени, сама отправляет
magic packet.

Обратная сторона: для платы плановое выключение выглядит точно так же, как
авария. Поэтому перед корректным выключением контроллер отправляет плате
`guard_snooze` — иначе система включала бы ПК, который пользователь только
что выключил.

Ключевая идея разделения: **всё, что должно происходить внутри
операционной системы, делает агент; всё, что требует присутствия в
физической сети или на проводах, делает ESP32.** Контроллер сам ничего не
исполняет — он маршрутизирует, хранит состояние и показывает интерфейс.

## 3. Почему такой стек

### Python + FastAPI для контроллера и агента

| Вариант | Почему не он |
|---|---|
| Go | Один статический бинарник — удобно, но кода вдвое больше, OpenAPI руками, PTY и статистика — вручную. Пользователь будет дописывать действия сам, и читаемость важнее скорости запуска. |
| Node/TypeScript | Тот же объём работы, но статистика системы и PTY хуже поддержаны. |
| Гибрид (контроллер Python, агент Go) | Два языка в личном проекте — двойная стоимость поддержки без выигрыша. |

FastAPI даёт OpenAPI из тех же моделей, которыми проверяются данные;
`psutil` закрывает статистику на трёх платформах; PTY и tmux — стандартная
библиотека. Установка через `uv` — одна команда и воспроизводимый lock-файл.

### ESP-IDF, а не Arduino

На машине уже установлен ESP-IDF 5.2.5 с полным тулчейном. ESP-IDF даёт из
коробки то, что в Arduino пришлось бы собирать из библиотек: NVS для
конфигурации, сторожевой таймер, разделы под OTA, событийную модель Wi-Fi
с корректным переподключением, `esp-mqtt` с последней волей (LWT).

### Никакого фронтенд-сборщика

Интерфейс — три файла: `index.html`, `app.js`, `style.css`. Ни npm, ни
шага сборки. Причины: страница должна открываться мгновенно на мобильной
связи, а править её можно любым редактором прямо на сервере. Единственная
внешняя библиотека — `xterm.js`, и она лежит в репозитории локально, а не
тянется с CDN: в домашней сети интернета может не быть.

### SSE, а не WebSocket, для обновлений

Поток состояний односторонний. Браузер переподключает `EventSource` сам,
и он проходит через любые прокси. WebSocket использован там, где он
действительно нужен, — в терминале.

## 4. Модель безопасности

### Четыре независимых рубежа

1. **Tailscale.** Контроллер слушает частный адрес и не имеет выхода в
   интернет. Но Tailscale — это транспорт, а не аутентификация: в тайлнет
   можно добавить чужое устройство (у автора проекта такое уже было —
   узел из чужого тайлнета `tailf1ffd1`). Поэтому вход обязателен и внутри.
2. **Сессия владельца.** Passkey (WebAuthn) как основной вход, пароль
   (argon2id) как аварийный. Сессия — JWT в httpOnly-cookie на 30 дней.
   Перебор пароля ограничивается по адресу источника.
3. **Токен агента.** Контроллер предъявляет агенту общий секрет в
   заголовке `X-Remo32-Agent-Token`. Без него агент не отвечает ничего,
   кроме `/ping`.
4. **Разделение действий и оболочки.** REST API не принимает команд —
   только идентификаторы действий, описанных в конфигурации.

### Почему пароль остаётся всегда

Passkey привязан к домену. Стоит контроллеру переехать на другой адрес —
и все ключи перестают подходить. Пароль здесь не «слабое звено», а
единственный способ не запереть себя снаружи собственной системы.

### Как устроены безопасные действия

В конфигурации лежит не строка для оболочки, а типизированное описание:

```toml
[[actions]]
id = "claude"
kind = "tmux"
workdir = "~/JII"
argv = ["claude", "-c"]
```

Каждый вид действия (`exec`, `shell_script`, `systemd_user`,
`systemd_system`, `tmux`, `desktop`) — отдельная модель со своей
проверкой, и каждая знает, как превратить себя в список аргументов.
`shell=True` в проекте не встречается ни разу. Глагол `systemctl`
ограничен белым списком, имя юнита проверяется регулярным выражением,
путь к скрипту обязан быть абсолютным.

Строка из технического задания `cd ~/JII && claude -c` выражается через
`workdir` и `argv` — тот же результат без интерпретации пользовательского
текста.

### Терминал

Самая мощная возможность, поэтому:

* выключен по умолчанию;
* требует разрешения **и** в контроллере, **и** в агенте — два независимых
  выключателя;
* браузер не подключается к агенту напрямую: контроллер проверяет сессию
  и проксирует поток, токен агента в браузер не попадает;
* каждое подключение и объём ввода пишутся в журнал аудита с правами 0600;
* работает от обычного пользователя, не от root.

### Что сознательно НЕ сделано

* Нет ручки «выполнить произвольную команду». Терминал — это интерактивная
  сессия с аудитом, а не удалённый `exec` по HTTP.
* Контроллер не умеет запускать процессы. Даже если его взломают, он может
  лишь просить агентов о том, что те и так разрешают.
* Прошивка не объявляет возможность `kvm`, пока переключателя нет:
  контроллер честно отвечает 501, а не делает вид, что переключил.

## 5. Состояния устройств

Пять состояний, и разница между ними принципиальна:

| Состояние | Значение |
|---|---|
| `ONLINE` | Агент ответил на последний опрос |
| `OFFLINE` | Опрос был и не удался нужное число раз подряд |
| `UNKNOWN` | Опроса ещё не было (контроллер только запустился) |
| `CONNECTING` | Идёт пробуждение или первая неудача после успеха |
| `ERROR` | Устройство отвечает, но неправильно |

`UNKNOWN` и `OFFLINE` не смешиваются намеренно: показывать «выключен»,
когда система просто ещё не проверяла, — это враньё пользователю.

Переход в `OFFLINE` требует нескольких неудач подряд
(`poller.offline_after_failures`), иначе одна потерянная датаграмма
заставляла бы интерфейс мигать.

Статистика при уходе в офлайн **не стирается**: она помечается как
устаревшая (`stale`) и показывается тусклой. Знать, что было пять минут
назад, полезнее, чем видеть пустоту.

## 6. Абстракция ESP32

```
Esp32Controller                     ← прикладные операции
      │
      ▼
Esp32Transport (протокол)
      ├── MockEsp32Transport        ← симулятор в процессе контроллера
      ├── HttpEsp32Transport        ← плата в домашней сети
      └── MqttEsp32Transport        ← плата через брокер, работает снаружи
```

Смена транспорта — одна строка в конфигурации. Проверено: одни и те же
операции отработали через мок, через HTTP к отдельному процессу-симулятору
и через MQTT-брокер `mosquitto` в контейнере.

Отдельно существует **самостоятельный симулятор** (`remo32-espsim`) —
процесс, который ведёт себя как плата: отвечает на команды, публикует
статус с retain, объявляет последнюю волю, умеет по команде «терять
Wi-Fi», «уходить в офлайн» и «случайно отказывать». Он нужен, чтобы
проверять поведение системы при сбоях, а не только в идеальных условиях.

Симулятор всегда сообщает `simulated: true`, и контроллер эту метку не
затирает — интерфейс обязан показывать, что железо не задействовано.

## 7. Два пути пробуждения

Magic packet не проходит через маршрутизаторы и через Tailscale — это
свойство широковещательных пакетов, а не недоработка. Поэтому путей два:

1. **Прямой.** Контроллер сам шлёт пакет. Работает, только если он в той
   же локальной сети, что и целевой ПК.
2. **Через ESP32.** Плата стоит дома и шлёт пакет изнутри сети. Работает,
   когда контроллер снаружи.

Контроллер пробует оба и сообщает в ответе, какой сработал. Порядок
задаётся `wol.prefer_esp32`.

**Как это решено.** Раньше здесь стояла нерешённая задача: когда оба ПК
выключены, контроллеру негде работать. Выбран третий из вариантов —
постоянно включённый узел, и им стал сам основной ПК. Проброс порта наружу
и зависимость от облачного брокера отпали.

Осталась одна ситуация, которую человек снаружи закрыть не может: основной
ПК умер сам. Её закрывает сторож на плате — не по команде, а самостоятельно.

### Сторож основного ПК

Живёт в прошивке (`components/r32_guard`), работает независимо от
контроллера и от телефона.

| Что | Как |
|---|---|
| Проверка | ICMP-пинг раз в 30 с, три пакета — один потерянный не считается пропажей |
| Ожидание | `grace` минут молчания перед первой побудкой (по умолчанию 10) |
| Повтор | `retry` минут между попытками (по умолчанию 15), не более `tries` раз |
| Нет Wi-Fi у платы | Проверка пропускается: нельзя отличить «ПК выключен» от «мы сами оторвались» |
| Плановое выключение | Контроллер шлёт `guard_snooze`, сторож молчит заданное время |
| Исчерпаны попытки | Состояние «попытки исчерпаны»: ПК, видимо, обесточен, долбить бессмысленно |

Два решения, которые стоит назвать явно. Первое: при отсутствии Wi-Fi
плата **молчит** — ложная побудка хуже пропущенной. Второе: если контроллер
не знает возможностей платы (она молчит в момент выключения), `guard_snooze`
всё равно отправляется — не предупредить опаснее, чем послать лишнюю
команду.

## 7а. Расписание

Правила «в такое-то время сделать то-то» живут в контроллере
(`schedule/service.py`) и редактируются с телефона.

| Решение | Причина |
|---|---|
| Время + дни недели, а не cron | Cron невозможно осмысленно править пальцем на телефоне |
| JSON в `data_dir`, а не в памяти | Перезагрузка раз в неделю не должна стирать расписание |
| Метка сработавшего слота | Тик планировщика чаще минуты; без метки правило стреляло бы несколько раз |
| Окно догона 15 минут | Контроллер, поднявшийся в полдень, не должен выполнять ночное правило |
| Ручной запуск не занимает слот | Нажатие «выполнить сейчас» в 20:00 не отменяет плановые 23:00 |
| Ошибка действия не роняет цикл | Выключенный ПК — обычное дело; результат пишется в правило и виден в интерфейсе |

## 8. Устойчивость к отказам

| Ситуация | Поведение |
|---|---|
| ПК выключен | `OFFLINE`, остальные ПК не затронуты, ответ 503 с понятным кодом |
| Агент перезапускается | Опрос восстановит состояние на следующем цикле |
| ESP32 недоступен | Состояние `OFFLINE`, контроллер продолжает работать |
| Брокер MQTT упал | Переподключение с растущей паузой до 60 с |
| Wi-Fi пропал на плате | Прошивка переподключается сама, пауза растёт до 60 с |
| Плата зависла | Сторожевой таймер (30 с) перезагружает её |
| Основной ПК умер сам | Сторож на плате поднимает его без участия человека |
| Одно правило расписания сломано | Остальные продолжают работать, ошибка видна в интерфейсе |
| Токены агента разошлись | Ответ 502 `agent_unauthorized` — **не** 401, иначе браузер выкинул бы владельца на экран входа из-за чужой ошибки |
| Датчик или GPU недоступен | Поле `null`, имя сборщика в `degraded`, остальная статистика собирается |
| Обрыв связи в терминале | Процессы живут в tmux, браузер переподключается сам |

## 9. Структура репозитория

```
Remo32/
├── packages/
│   ├── remo32-core/        общие модели, протокол, HTTP-слой, логирование
│   ├── remo32-controller/  API, аутентификация, реестр ПК, ESP32, веб-интерфейс
│   ├── remo32-agent/       служба на управляемом ПК
│   └── remo32-espsim/      самостоятельный симулятор платы
├── firmware/               прошивка ESP-IDF для ESP32-S3
├── config/                 примеры конфигурации (без секретов)
├── deploy/                 systemd, polkit, скрипт установки
├── docs/                   схема подключения, состояние сессии
└── tests/                  150 тестов
```

Разделение на пакеты не косметическое: агент ставится на другую машину
и не должен тянуть за собой зависимости контроллера (`webauthn`,
`aiomqtt`, `argon2`).

## 10. Принятые компромиссы

* **Хранилище — файлы, не база данных.** Passkey и ключ сессий — это
  единицы записей. SQLite добавил бы миграции и резервные копии ради
  ничего.
* **Отзыв сессий живёт в памяти.** После перезапуска контроллера список
  отозванных теряется, но сессии и так подписаны ключом, а выход из
  системы действует немедленно — этого достаточно для одного владельца.
* **Опрос вместо подписки для ПК.** Агент не «звонит» контроллеру сам:
  так проще, и агент остаётся полностью пассивным. Цена — задержка до
  5 секунд в отображении состояния.
* **Windows и macOS реализованы по документации и не проверены.** Обе
  машины владельца на Linux. Код изолирован в адаптерах, интерфейс
  задан, но честно помечен как непроверенный.

## 11. Что проверено на железе, а что нет

### Проверено на настоящей плате (2026-09-03)

Прошивка залита в ESP32-S3 и запущена:

* загрузка без ошибок, `rst:0x1 (POWERON)`, чистый старт;
* инициализация GPIO (4 вывода по таблице);
* последовательная консоль: `help`, `show`, `save`, `guard`;
* настройки сторожа **переживают полную перепрошивку приложения** — NVS
  работает как задумано;
* найден и исправлен баг, который проявляется только на железе: команда
  `guard` роняла плату по нулевому указателю, если устройство ещё не
  настроено (`app_main` завершается до `r32_guard_start`, а команда уже
  зарегистрирована).

### PSRAM: неисправен, подтверждено

Гипотеза «PSRAM может быть плохим» проверена прямо:

| Проверка | Результат |
|---|---|
| `esptool flash_id` | `Features: WiFi, BLE, Embedded PSRAM 8MB (AP_3v3)` — физически есть |
| Инициализация на 80 МГц | `good-die: 0x01 (Pass)`, `Found 8MB PSRAM device` — определяется |
| Обращение к памяти на 80 МГц | **зависание**, затем `rst:0x10 (RTCWDT_RTC_RST)` |
| То же на 40 МГц | **то же зависание** — дело не в частоте |

`good-die: Pass` — заводской флаг в регистре самого чипа, а не результат
проверки. Память определяется, но первое же реальное обращение вешает
систему насмерть. Вывод: `CONFIG_SPIRAM` остаётся выключенным навсегда, и
эта плата **непригодна для задач с кадровым буфером** — в частности, для
тачскрина с LVGL.

### Всё ещё не проверено

Помечено в документации как `HARDWARE TEST REQUIRED`:

* поведение Wi-Fi на настоящей плате (пароль сети вводит владелец);
* отправка magic packet прошивкой;
* **сторож основного ПК в работе**: ICMP-пинг из прошивки, отсчёт
  grace-периода, реальная побудка умершего ПК;
* чтение уровня на входах GPIO;
* любая электрическая схема подключения к материнской плате;
* работа сторожевого таймера при реальном зависании;
* устойчивость встроенного PSRAM (он выключен, но не проверялся).

Проверено в программной части: сборка прошивки под ESP32-S3, протокол
обмена (включая `guard_snooze`), все три транспорта, поведение при сбоях,
весь код контроллера и агента, планировщик расписаний, управление
подсветкой через OpenRGB на настоящем железе этого ПК.
